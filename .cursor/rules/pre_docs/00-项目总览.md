# 项目总览 — MiniMax-H3 双路视频生成服务

> Spec 文档 · 生成于 2026-08-22 · 基于仓库当前 HEAD 全量代码阅读

## 一句话定位

在单机上编排多个 ComfyUI 实例（每实例绑一张 GPU），对外提供**异步文生视频（含音轨）** HTTP API，并附带 OpenAI 兼容端点供 ClipForge 等上层应用直连。

## 核心数据流（文生视频）

1. 客户端 `POST /api/v1/generate`（prompt + 分辨率 + 时长 + seed + steps）
2. `api_server.build_prompt()` 把参数映射成 **14 节点 ComfyUI graph**（见 `api-workflow.md`）
3. `_pick_worker()` 并发查询每个 worker 的 `/queue`，选 running+pending 最少的
4. `_submit_lock` 串行化「选 worker + 提交」，防并发读旧队列
5. POST 到 worker 的 `/prompt`，拿到 `prompt_id` 返回给客户端（HTTP 202）
6. 客户端轮询 `GET /api/v1/task/{id}`，网关查 worker `/history/{id}` 映射状态
7. 完成后从 history `outputs` 提取视频文件名，回填 `videos` URL（指向网关自身的代理端点）
8. 客户端 GET 该 URL → 网关从对应 worker `/view` 拉流转发

## 关键设计决策

| 决策 | 原因 |
|---|---|
| 每实例 `--cuda-device` 独占一张 GPU | 避免多进程争抢显存；4090 49GB 单卡装不下双实例 |
| worker 1 独立 `--output-directory` / `--user-directory` | 防两实例写同一个 `comfyui.db` / 文件计数器冲突 |
| API 层做 `/view` 代理而非暴露 worker 端口 | 外部只需访问 8000 一个端口 |
| `_video_worker` 记录"文件名→worker"映射 | 视频产出后按来源 worker 精确代理，miss 时全 worker 回退 |
| OpenAI 兼容层复用同一套提交逻辑 | ClipForge 的 `CustomOpenAIProvider` 可零改动接入 |
| `duration → length` 对齐到 17k+5 帧网格 | MiniMax H3 模型的硬约束（`nodes_minimax_h3.py:34`） |
| 帧数下限 5、上限 `MAX_DURATION=20s` | 模型训练区间 5–15s，>15s 未验证，20 为保守上限 |

### 过渡期说明（单卡 → 双卡）

- `comfy-gpu1` 当前的 crash loop（`cudaGetDeviceCount() Error 304`）是**第二张卡尚未插入**所致，不是配置错误。
- **扩容操作**：物理插入第二张 4090 → `pm2 restart comfy-gpu1` → API 自动开始向其分发任务（`_pick_worker` 按 `/queue` 负载自动感知，无需重启 api_server）。
- 过渡期可选的临时止血（避免 PM2 反复拉起重启计数）：
  ```bash
  pm2 stop comfy-gpu1 && pm2 save
  # 第二张卡插入后：
  pm2 start comfy-gpu1 && pm2 save
  ```
  注意：过渡期 `COMFY_HOSTS` 仍指向两个 worker，`_pick_worker` 会对挂掉的 8189 记 load=∞ 自动绕开，**单卡期间服务不受影响**，只是 `/health` 显示 `degraded`。

### 待改进项

1. **公网 IP 泄露在 `client_example.py:17`**（`http://117.50.216.253:8000`）——建议改为环境变量注入，避免 IP 硬编码随仓库扩散。
2. **CORS 全开**（`allow_origins=["*"]`）：公网暴露时建议收紧到 ClipForge 域名。
3. **`/api/v1/task` 无鉴权**：任何知道 task_id 的人可拉取视频，公网部署需加 token。
4. **`_worker_assign` 为进程内存**：API 重启后旧任务查询会 fallback 到 worker 0（见 `01-架构设计.md` §2.3）。
