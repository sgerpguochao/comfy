## 11.1 测试思路与脚本说明

### 11.1.1 为什么"通过接口"

`generate_h3.py` 是一个 CLI 包装脚本，对 HTTP 接口做了封装。直接打接口可以：

- **验证 API 行为本身**（而非包装脚本）
- **精确看到每个端点的真实响应**（422 / 502 / 业务错误 vs CLI 包装后的"exit 1"）
- **贴近上游业务集成场景**（如 ClipForge 直接调 API）

### 11.1.2 用到的端点（与 `api_server.py` 一一对应）

| HTTP | 端点 | 用途 |
|------|------|------|
| GET | `/health` | 健康检查 |
| POST | `/api/v1/upload` | 上传本地图片/BGM 到 ComfyUI 共享 input 目录 |
| POST | `/api/v1/generate` | 提交生成任务，返回 `task_id` |
| GET | `/api/v1/task/{task_id}` | 轮询任务状态与视频 URL |
| GET | `/api/v1/video/{filename}` | 下载产物视频 |

完整接口字段定义见 `comfy/api_server.py:209-223` 的 `GenerateRequest`（Pydantic）。

### 11.1.3 脚本执行流程

```
1. 调 /health → 若未就绪，自动调 start_services.sh start
2. 准备素材：用 PIL 生成首帧 / 尾帧 PNG，BGM 用项目已有的 bgm_test.mp3
3. 调 /api/v1/upload 把图片/BGM 上传到共享 input 目录，拿到裸文件名
4. 按 case 顺序调 /api/v1/generate → 轮询 /api/v1/task/{id} → 下载 /api/v1/video/{name}
5. 校验类 case 直接调接口，期望返回 4xx
6. 全程日志写到 /home/ubuntu/minmax/comfy/playground/run_7cases_http_<时间戳>.log
```

### 11.1.4 用法

```bash
# 跑全部 13 个 case（6 功能 + 7 校验）
cd /home/ubuntu/minmax/comfy && python playground/run_7cases_http.py

# 只跑指定 case
python playground/run_7cases_http.py --only 1 3 5

# 只跑校验类（不消耗 GPU，约 1 秒）
python playground/run_7cases_http.py --quick
```

### Case 4：图生视频 i2v + 静音（v2 修复版）

**v1 失败回顾**：第一次跑 Case 4 时请求体**不带 prompt**：

```json
{
  "first_frame": "i2v_xxxxxx.png",
  "duration": 5, "seed": 14111, "steps": 10,
  "no_audio": true
}
```

实际响应是 **HTTP 422**：

```json
{"detail":[{"type":"missing","loc":["body","prompt"],
"msg":"Field required",
"input":{"first_frame":"...","duration":5,"seed":14111,"steps":10,"no_audio":true}}]}
```

**根因**：`GenerateRequest.prompt: str = Field(..., ...)` 是**必填**（`api_server.py:210`）。HTTP 接口不会像 `generate_h3.py` CLI 那样自动填充默认提示词。

**v2 修复版**（本测试采用方案 3）：在请求体里显式传一个描述动效的 prompt（与 `generate_h3.py:50` 的 `IMAGE_DEFAULT_PROMPT` 等价）：

```http
POST /api/v1/upload       （上传首帧）
  → {"filename": "i2v_77b983e85138.png"}

POST /api/v1/generate
{
  "prompt": "保持画面主体和构图不变，让场景自然流畅地动起来，画面连贯稳定",
  "first_frame": "i2v_77b983e85138.png",
  "duration": 5, "seed": 15631, "steps": 10,
  "no_audio": true
}
```

**实际响应**：

```json
{
  "task_id": "36467829-f7d0-4917-821c-c746591bb487",
  "status": "queued",
  "worker": 0,
  "frame_count": 124,
  "duration": 5.0
}
```

**轮询**：`status: queued` (0s) → `status: success` (150s)。

**完成响应**：

```json
{
  "videos": ["http://127.0.0.1:8000/api/v1/video/muted_36467829-...mp4"],
  "audio_processed": true
}
```

✅ **v2 通过**，端到端耗时 **160.2 秒**，产物 121 KB，视频时长 5.167 秒。

> 修复后的 Case 4 视频名以 `muted_` 开头，确认走了静音剥离分支（`api_server.py:_post_process` 的 `-an` 路径）。

**生产启示**：直接调 API 的业务**必须传 prompt**，即使传图也要给模型一个"动起来"的描述（与 CLI 的 `IMAGE_DEFAULT_PROMPT` 一致）。建议在 API 文档中显式标注这一点。

### Case 5：首末帧生成 + 静音 + BGM（最复杂组合）

**HTTP 请求**：

```http
POST /api/v1/upload       （首帧）
POST /api/v1/upload       （尾帧）
POST /api/v1/upload       （BGM）

POST /api/v1/generate
{
  "first_frame": "i2v_xxx.png",
  "last_frame":  "i2v_xxx.png",
  "prompt": "画面从夕阳黄昏平滑过渡到夜晚海洋，色调由暖橙渐变为深蓝",
  "duration": 5, "seed": 14112, "steps": 10,
  "no_audio": true,
  "bgm": "i2v_xxx.mp3", "bgm_volume": 0.5
}
```

**完成响应**：视频以 `muxed_` 开头。

✅ 通过。组合了**首帧 + 尾帧 + 静音 + BGM** 四个音频/视频配置。

**后处理 ffmpeg filter_complex 流程**：

1. `-i src.mp4` 主视频（无音频，因 `no_audio=true`）
2. `-stream_loop -1 -i bgm.mp3` BGM 循环
3. filter_complex: `aformat=...:stereo, volume=0.5, atrim=0:5.0, afade=t=out:st=3.0:d=2.0`
4. `amix=inputs=1:duration=first`（只有 BGM 一路音频）
5. `-c:v copy -c:a aac -b:a 192k`（视频流复制，音频转 AAC）

### Case 75：`first_frame` 引用无法识别

```http
POST /api/v1/generate
{"prompt": "test", "first_frame": "not-a-url-or-data-uri", "duration": 5}
```

**响应 502**：


✅ 正确拒绝。接口层的 `_is_uploaded_ref`（`api_server.py:323-325`）只识别 4 种形式，其他都视为裸文件名传给 ComfyUI LoadImage 节点，节点找不到文件抛错。

### Case 76：GET 不存在的 task_id（探针）

```http
GET /api/v1/task/00000000-0000-0000-0000-000000000000
```

**响应 200**：

```json
{"task_id":"00000000-...","status":"queued"}
```

❌ 脚本期望 4xx，实际 200。这是 API 设计选择：

```707:715:comfy/api_server.py
async def task_status(task_id: str, request: Request):
    idx = _worker_assign.get(task_id, 0)
    async with _workers[idx].get(f"{_worker_url(idx)}/history/{task_id}") as resp:
        history = await resp.json()
    entry = history.get(task_id)
    if entry is None:
        return {"task_id": task_id, "status": "queued"}
```

未找到的任务统一返回 `status="queued"`，客户端通过轮询超时自行判断。**建议**改为 404，但属于行为差异非 bug。

### Case 77：上传 .txt 当图片（探针）

```http
POST /api/v1/upload
multipart; file=fake.txt (5 bytes)
```

**响应 200**：`{"filename": "i2v_xxx.txt"}`

❌ 脚本期望 415/400，实际 200。接口只校验大小（30MB），不限 MIME。**属于行为差异**——客户端需要自行校验类型。

| Case | 提交→下载完成 | 队列+推理 | 后处理+下载 | 产物前缀 | 视频时长 |
|------|--------------|----------|-----------|---------|---------|
| 1 文生 t2v | **220.2s** | 210s | <1s | `minimax_` | 5.167s |
| 2 文生+静音 | **220.3s** | 210s | <1s | `muted_` | 5.167s |

| 平均 | **197.4s** | 186.7s | ~10s | — | 5.169s |

**耗时分布观察**：

- **队列+推理**占总耗时 90%+，是瓶颈
- **图生视频比文生视频快 40-50 秒**（首帧已编码进 latent，采样收敛更快）
- **后处理（混流）几乎免费**（<10s），其中 ffmpeg `-c:v copy` 直接复用视频流
- **下载时间可忽略**（<1s，本地网络）
- 端到端耗时波动主要在 ComfyUI 任务调度（worker 0 排队 0-220s 不等）

### 优化建议（基于耗时分析）

1. **减步数**：`steps=10 → 8` 可省约 15-20% 推理时间，画质损失极小
2. **图生优先**：对素材充足的场景，优先用 i2v/fl2va 路径，比 t2va 快 20%
3. **错峰调度**：6 个任务顺序跑总耗时 1024s；若并发跑（2 worker）理论可压到 510s
4. **跳过上传**：同一张图复用 task 时，不要每次都 `/api/v1/upload`，直接传裸文件名即可

## 11.11 建议改进（基于本次接口测试）

1. **`prompt` 必填导致图生视频失败**（**优先级最高**）：API 应该支持 `prompt` 缺省（如 CLI 行为），否则直接调 API 的业务会被 422 阻断。
   - 修复：`api_server.py:210` 改为 `prompt: Optional[str] = Field(None, description="...")`，在 endpoint 中根据 mode 补默认 prompt。
2. **`GET /api/v1/task/<unknown>` 返回 404**：当前返回 200+queued 误导客户端（建议加 `if history entry is None and task_id not in _worker_assign: raise 404`）。
3. **`POST /api/v1/upload` 校验文件类型**：当前接受任意 30MB 以下文件，建议校验 MIME 或扩展名。
4. **`POST /api/v1/generate` 的 `first_frame` 引用错误返回 502**：应该返回 400（用户输入错误），而非 502（ComfyUI 节点错误透传）。
5. **进度查询**：当前 `/api/v1/task/{id}` 仅返回终态，建议加 `progress` 字段（从 ComfyUI `/prompt` 当前状态推断）。
