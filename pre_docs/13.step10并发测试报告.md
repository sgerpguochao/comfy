**验证点**：

1. **提交零串行化**：6 个请求并发提交总耗时 **0.07s**（单个仅 ~0.06s），证明 `_pick_lock` 小锁 + 上传/POST 均在锁外的改造有效，无旧 `_submit_lock` 的排队累积
2. **双卡分配完美均衡 3:3**：`_local_load` 预留式调度按 `(remote_queue + local_inflight)` 最小选卡，6 个并发请求被交替分到两张卡，无"全砸一张卡"现象
3. **帧数网格**：`duration=5` → `frame_count=124`（17k+5 网格，k=7），实际视频时长 5.167s，与《3.部署与运行》的映射表一致

### 13.4.2 单任务耗时分析

本次单任务平均 ~300s（第一梯队 974/2≈490s 含队列等待，第三梯队 1296/3≈432s）。与《10.测试过程文档》串行基线的 ~200s 相比偏慢，原因：

1. **帧数差异**：本次 `duration=5s` → 124 帧；文档 10 基准虽同为 5s，但文档 12 基准是 `3s`/73 帧（帧数 -41%）
2. **首轮模型冷加载**：每卡第 1 个任务含 ~10 分钟模型加载（48GB 显存需分页加载 H3 模型）
3. **混流后处理串行**：Case 3 的 edge-tts 合成、Case 5/6 的 BGM 混流在 API 进程内串行执行，占据部分端到端时间

**吞吐对比**（同硬件同脚本，仅 steps/duration 不同）：

| 场景 | 单任务均耗时 | 6 任务总耗时 | 吞吐 |
|------|-------------|-------------|------|
| 文档 12 基准（3s/73帧，4 并发） | ~110s | 204.6s（4 任务） | ~1.2 tasks/min |
| **本次（5s/124帧，6 并发）** | ~440s（含冷启） | 1344.5s | 0.27 tasks/min |

> 推论：稳态（模型已加载）下 5s/124 帧单任务预计 ~250-300s，6 任务双卡理论总耗时 ~750-900s。冷启动占了本次总耗时的 1/3。

## 13.5 结论

### ✅ 通过项

1. **异步双卡并发**：提交 0.07s 无串行化，worker 分配 3:3 均衡，符合方案 A 改造预期
2. **全 6 case 功能路径**：t2v / t2v+静音 / t2i2v+口播 / i2v+静音 / 首末帧+BGM / t2v+原声+BGM 全部成功
3. **音频后处理全通**：静音剥离、edge-tts 口播混流、BGM 循环混流、三轨叠加全部按预期生效
4. **图生视频自适应**：首帧 1024×768 → 输出 1024×768，画布对齐正确
5. **帧数网格约束**：5s → 124 帧 → 5.167s 实际时长，符合 17k+5 网格

### ⚠️ 已知问题与改进建议

1. **模型冷加载慢**（~10 min/卡）：首轮任务显著偏慢。建议生产环境预热（启动后先提交一个 dummy 任务），或探索模型常驻显存的 keep-alive 配置
2. **混流后处理在 API 进程内串行**：Case 3/5/6 的 edge-tts + ffmpeg 在 API 进程执行，多任务同时完成后处理会排队。建议改后台任务队列（asyncio.create_task 或独立 worker）
3. **`bench_6cases_concurrent.py` 硬编码外部路径**：`import /home/ubuntu/minmax/comfy/playground/run_7cases_http.py` 在仓库外。建议改为相对导入或把公共函数（素材生成、upload）下沉到共享模块
4. **venv 依赖未固化**：`python-multipart` 缺失导致 upload 500，暴露出 `requirements.txt` 缺失。建议补 `requirements.txt`（fastapi、uvicorn、aiohttp、requests、python-multipart、edge-tts、Pillow）
