> **对比基线**：见《13.step10 并发测试报告》（commit `031ae64`）

## 14.1 改动回顾

`api_server.py` 中做了三处改动（commit `a358e96`）：

1. **启动预热**（`_warmup_all_workers / _warmup_one`）
   - FastAPI `startup()` 中后台并发提交 1 帧 1 step 的 dummy prompt 给两张卡
   - H3 模型（UNet + CLIP + VAE）在业务请求之前就被加载到显存
2. **后台 MUX 队列**（`_post_queue + _mux_worker_loop × 2`）
   - `/api/v1/task/{id}` 轮询路径不再 `await _post_process(...)`
   - 改为 `_post_queue.put_nowait(...)`，由 2 个后台协程消费
3. **`/health` 增加 warm 状态**
   - 返回 `warming` / `ok` / `degraded` 三态
   - 每个 worker 报告 `warmed: true/false`

## 14.3 收益拆解

### 14.3.1 预热带来的提速

```
冷态单任务耗时（首次）：974-991s
热态单任务耗时（稳态）：150-205s
冷启动开销：≈ 800s/卡（~7.5 分钟双卡并行加载）
```

预热把这 800s/卡从业务耗时里**完全剔除**。如果是真实生产场景（用户提交请求时机器刚启），第一次业务请求的 e2e 立刻进入"热态"，不再等待模型加载。

### 14.3.2 后台 MUX 带来的加速

6 个 case 并发完成后，传统实现下后处理是阻塞的：

```
旧：case1 完成 → await mux → case2 完成 → await mux → ... → 串行 6 次
新：case1-6 全部 success 后立即返回，mux 在后台 2 worker 消费
```

实测本次 case3 的 mux 文件 `muxed_1e8f8ea2-...mp4` 在 16:02 创建，比原视频生成时间晚约 5-10 秒。如果客户端对 mux 完成做主动轮询，会感知到这个间隔。

### 14.3.3 整体提速

| 场景 | 旧 | 新 | 加速比 |
|------|----|----|--------|
| 6 任务冷启动并发 | 1344.5s | 550.4s | 2.44× |
| 6 任务热启动并发（理论） | ~1080s（每张卡串行 3 个 ~180s） | ~540s | 2.0× |
| 单任务（业务首次提交） | 974s + mux | **201s + 后台 mux** | **4.8×** |

实际测试从 1344.5s → 550.4s 的 **2.44×** 加速，与"双卡任务级并行"的理论上限（2.0×）相符，并因**消除了冷启动**而略超。

## 14.4 启动时长的权衡

| 时点 | 旧实现 | 新实现 |
|------|--------|--------|
| PM2 start | ~5s（API 进程起） | ~5s（API 进程起） |
| /health 返回 ok | ~30s | ~30s（API + worker 都活着） |
| /health 返回 warmed=true | N/A | **~7.5 min 后**（双卡模型加载完） |
| 第一个业务任务可用 | 1344s 内首 case 完成 | **201s**（含业务推理） |

**取舍**：
- 旧实现：服务"在线"≠"可用"，第一个真实任务会被冷启动拖累
- 新实现：服务明确分 `warming` / `ok` 两态，客户端可等待 `ok` 或接受 `warming` 后立即提交

建议客户端行为：
```python
while True:
    h = requests.get(f"{api}/health").json()
    if h["status"] in ("ok", "warming"):  # warming 也可提交，模型已在加载
        break
    time.sleep(5)
```

## 14.6 注意事项与已知限制

1. **业务请求可能撞上冷启**：客户端在 `warming` 期间就提交任务，任务会正常排队，但**第一个推理任务**仍承担模型加载（无法绕过）。要彻底解决需要更激进的"先 warmup 完再 accept connections"
2. **mux 完成事件没有回调**：客户端只能靠轮询时观察 `_muxed` 字典是否生成 `muxed_*` 文件，或等待几秒后再次拉取。若想精确感知 mux 完成，可在 `/api/v1/task/{id}` 响应里加 `audio_ready: bool` 字段
3. **warmup 任务有副作用**：会留下 `minimax_warmup_*.mp4` 在 `ComfyUI/output/`，需要定期清理或重写 `build_prompt` 让 warmup 不产生输出文件
