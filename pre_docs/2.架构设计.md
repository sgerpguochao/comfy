## 2.2 双 GPU 隔离设计

| 维度 | GPU 0（worker 0） | GPU 1（worker 1） |
|------|-------------------|-------------------|
| 端口 | 8188 | 8189 |
| 输出目录 | `ComfyUI/output/` | `ComfyUI/output/gpu1/` |
| 用户目录 | `ComfyUI/user/` | `ComfyUI/user/gpu1/` |
| 数据库 | 默认 `comfyui.db` | `user/gpu1/comfyui.db` |
| 共享部分 | `ComfyUI/input/`、`ComfyUI/models/` | 同左 |

> 关键点：**input 目录与 models 目录是共享的**，避免两个 worker 各存一份图片/模型浪费磁盘；**输出与数据库必须隔离**，否则两个实例的 `image_counter` 会冲突，覆盖彼此的视频。

## 2.3 调度策略

```python
async def _pick_worker() -> int:
    """选择队列（运行中+排队中）最短的 worker；全部不可达时按轮询兜底。"""
    best, best_load = 0, 10 ** 9
    for i in range(len(COMFY_WORKERS)):
        try:
            data = await (await _workers[i].get(f"{_worker_url(i)}/queue")).json()
            load = len(data.get("queue_running", [])) + len(data.get("queue_pending", []))
        except Exception:
            load = 10 ** 9  # 不可达
        if load < best_load:
            best, best_load = i, load
    if best_load == 10 ** 9:  # 所有 worker 都不可达
        best = _rr % len(COMFY_WORKERS)
        _rr += 1
    return best
```

- 选 **min(queue_running + queue_pending)**，避免长任务堆积
- 提交时通过 `_submit_lock` 串行化，防止读到旧队列长度
- worker 不可达时按 round-robin 兜底（让请求至少能尝试）

## 2.4 任务生命周期

```
提交 ──► 选 worker ──► (上传图片) ──► 调 /prompt ──► 立即返回 task_id (202)
                                                  │
                                                  ▼
                                          客户端轮询 /api/v1/task/{id}
                                                  │
                                                  ▼
                                       worker history.completed = true
                                                  │
                                                  ▼

                                                  │
                                                  ▼

```

## 2.5 ComfyUI Prompt 图结构

API 服务**不调用 ComfyUI 工作流编辑器**，而是直接构造 `/prompt` 所需的 JSON 图（节点列表 + 连线）。核心 14 节点：

```1:14:comfy/api_server.py
UNETLoader  ─┐
             │
CLIPLoader  ─┼─► MiniMaxH3ImageToVideo ─► SamplerCustomAdvanced ─► VAEDecode ─┐
             │                                                                  ├─► CreateVideo ─► SaveVideo (mp4)
VAELoader   ─┘                                                                  │
VAELoader (audio) ───────────────────────────────────────► VAEDecodeAudio ─────┘
```

可选节点：
- `LoadImage`（节点 15/16）：当 `first_frame` 或 `last_frame` 存在时挂入
- `LoadImage`（节点 15..23）：ref2va 路径下挂入最多 9 张参考图

## 2.6 状态持久化

`api_state.json` 实时持久化 4 类元数据：

```json
{
  "voiceover": { "<task_id>": ["文案", "音色"] },
  "noaudio":   ["<task_id>", ...],
  "bgm":       { "<task_id>": ["BGM 引用", 音量] },
  "assign":    { "<task_id>": worker_idx }
}
```

写入采用 `tmp + os.replace` 原子替换，避免半写状态。**重启 API 后，仍能恢复"待后处理"任务**——这是为什么 worker 必须持久化输出文件而不只是缓存结果。

## 2.7 关键设计决策

| 决策 | 原因 |
|------|------|
| 多 worker 而非单 worker 排队 | 单卡显存/算力上限就是上限；多卡才能水平扩展 |
| `_submit_lock` 串行提交 | 避免并发读到旧队列长度导致分配失衡 |
| 共享 `input/` 隔离 `output/` | 上传图只一份（节省 IO）、输出文件不冲突 |
| 后处理在 API 层而非 ComfyUI 内 | ComfyUI 节点调 TTS/ffmpeg 难维护；API 层 ffmpeg 更可控 |
| api_state.json 而非 SQLite | 任务元数据极少（KB 级），JSON 读写足够且易调试 |
| OpenAI 兼容端点 | ClipForge 等下游期望统一协议，无需改造客户端 |
